### 1. У вас от 45 до 60 минут, чтобы спроектировать фичу iOS-приложения на доске. Как распределить время и что на самом деле оценивает интервьюер?

Первые десять минут уточняйте требования, затем набросайте архитектуру клиента и API, а потом углубитесь в одну-две части, которые сложны именно на телефоне. Оценивают умение рассуждать о компромиссах с учётом ограничений iOS, а не количество квадратиков на схеме.

### 2. REST, GraphQL или gRPC: какой стиль API вы предложите для iOS-клиента и чего каждый из них стоит приложению?

По умолчанию берите REST с JSON: `URLSession`, `Codable`, HTTP-кэш и любой отладочный прокси работают из коробки. GraphQL окупается, когда многим экранам нужны разные срезы многих сервисов, gRPC, когда компания уже живёт на protobuf или нужен стриминг; оба переносят работу в клиент.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73902)

### 3. Почему offset-пагинация показывает дубли и пропуски в ленте, которая меняется, пока её листают, и что исправляет курсор?

Offset отсчитывает строки сверху, поэтому каждый пост, добавленный или удалённый выше пользователя, сдвигает окно: вставка повторяет последний элемент прошлой страницы, удаление пропускает один. Курсор указывает на последний полученный элемент и просит то, что идёт после него, и вставки сверху ему не мешают.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73903)

### 4. Каждый экран должен быть «свежим», поэтому на холодном старте приложение шлёт сорок запросов. Какие данные вы кэшируете, на сколько и где устаревшие данные допустимы?

Спрашивайте не о том, может ли значение устареть, а о том, чего это стоит для каждого вида данных. Большинство из сорока запросов тянут конфиг, справочники и контент: их можно сразу показать с диска и обновить в фоне. Лишь немногое, вроде баланса или цены при оплате, нужно запросить, прежде чем верить.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73904)

### 5. Главный экран банка показывает шесть виджетов из шести сервисов и остаётся пустым, пока не ответит самый медленный. Что вы поменяете на клиенте и на бэкенде?

Пусть каждый виджет грузится, падает и повторяет запрос сам, начиная с последнего значения из кэша, чтобы экран не зависел от самого медленного сервиса. На бэкенде дайте экрану один агрегирующий эндпоинт с дедлайном на каждую секцию, который отдаёт частичный результат, а не ждёт всех.

### 6. Найдите баг: на слабой сети быстро поставьте лайк и тут же снимите его: сердечко остаётся закрашенным, хотя на сервере лайка нет.

```swift
@MainActor final class PostCellModel {
  private(set) var post: Post
  private let api: any LikeAPI
  init(post: Post, api: any LikeAPI) { self.post = post; self.api = api }

  func likeTapped() {
    post.isLiked.toggle()                       // optimistic: the heart fills at once
    post.likeCount += post.isLiked ? 1 : -1
    Task {
      do { try await api.toggleLike(postID: post.id) }
      catch {
        post.isLiked.toggle()                   // roll back
        post.likeCount += post.isLiked ? 1 : -1
      }
    }
  }
}
```

Между двумя относительными запросами `toggleLike` возникает гонка, а откат переворачивает текущее состояние вместо того, чтобы вернуть серверное: когда первый запрос падает по таймауту уже после того, как сервер его применил, его `catch` снова закрашивает сердечко, очищенное вторым тапом.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73906)

### 7. Запрос на оплату отвалился по таймауту, и пользователь снова нажимает «Оплатить». Как клиент и API гарантируют, что карту спишут только один раз?

Ключом идемпотентности, который привязан к платежу, а не к запросу: приложение создаёт его один раз на заказ, сохраняет до отправки и переиспользует при каждом повторе, а сервер сохраняет первый результат под этим ключом и на любой повтор возвращает его вместо нового списания.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73907)

### 8. Распродажа должна закончиться в полночь, но часть пользователей открывает её и на следующее утро. Каким часам доверяет приложение и кто обеспечивает окончание?

Никаким часам на устройстве: дату можно поменять в Настройках, а «полночь» в каждом поясе своя. Окончание задаёт сервер как абсолютный момент и после него отказывает в покупке; приложение только показывает его по времени сервера и монотонным часам, которые не зависят от Настроек.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73908)

### 9. Спроектируйте ленту приложения вроде Instagram: поток данных, пагинация, предзагрузка, медиа и возврат пользователя к тому же посту после перезапуска.

Лента представляет собой локальный кэш, за которым следит UI: репозиторий подгружает страницы по курсору в хранилище, список рисуется из хранилища, медиа грузится с опережением скролла в размере ячейки, а позиция сохраняется как id якорного поста, чтобы перезапуск вернул пользователя туда же.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73909)

### 10. Спроектируйте просмотр сторис как в Instagram: что вы предзагружаете, сколько видеоплееров держите живыми и каков бюджет памяти?

Предзагружайте на шаг вперёд в каждом направлении, куда может пойти пользователь: следующий сегмент текущей сторис и первый сегмент следующего человека. Держите два-три плеера для текущего и следующего сегмента и переиспользуйте их, а память считайте в декодированных полноэкранных кадрах.

### 11. Спроектируйте публикацию объявления на маркетплейсе с десятью фото: сжатие, очередь загрузки, повторы и черновик, который переживает убийство приложения.

Сначала сохраните черновик и обработанные фото локально, загружайте каждое фото задачей из файла в фоновой `URLSession`, а объявление создавайте идемпотентным запросом, когда у всех фото есть серверный id.

### 12. Спроектируйте клиент мессенджера вроде Telegram: транспорт, статусы сообщений, локальное хранилище, порядок и что происходит офлайн или в фоне.

Чат живёт в локальной базе: UI рисуется из неё, исходящее сообщение сначала записывается туда с клиентским id, а слой синхронизации пользуется сокетом, пока приложение открыто, и догоняет пропуски по номеру последовательности. В фоне работу берут на себя APNs и notification service extension.

### 13. Спроектируйте отслеживание курьера в реальном времени: как его координаты попадают на экран клиента и что меняется, когда приложение в фоне или телефон заблокирован?

Приложение курьера шлёт на сервер прореженные точки геолокации, сервер привязывает их к дороге и пушит клиенту через сокет, пока открыта карта. Когда клиент уходит из приложения или блокирует телефон, эстафету принимает Live Activity, обновляемая пушами: замороженное приложение ничего не получает.

### 14. Как бы вы построили собственный слой аналитики приложения: пакетная отправка событий, хранение офлайн, сэмплирование, учёт согласия и смена вендора без правок в фичах?

Фичи вызывают один типизированный API `track`, который сразу возвращает управление; события попадают в очередь на диске, уходят сжатыми пачками с уникальным id у каждого и раздаются адаптерам вендоров за протоколом. Согласие и сэмплирование решаются один раз, в начале этого конвейера.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73914)

### 15. Когда server-driven UI того стоит и как старая версия приложения справляется с компонентом, которого никогда не видела?

Он окупается на экранах, которые продукт перестраивает каждую неделю (главная, промо, раскладки каталога), где узкое место в App Review и медленных обновлениях. Старые сборки справляются: запрос сообщает, какие компоненты сборка умеет рисовать, а неизвестный тип декодируется в фолбэк и не роняет экран.

### 16. Дюжина команд выпускает банк, такси и еду в одном iOS-супераппе. Как его устроить, чтобы ни одна команда не замедляла запуск и чужие релизы?

Как тонкий хост на общем платформенном слое с парой модулей на бизнес: маленький интерфейсный модуль, который импортируют другие команды, и реализация, которую линкует только хост. При запуске ничего не стартует, бюджеты проверяются в CI, а фичи выходят выключенными за флагами в общем релизном поезде.

[Полный ответ →](https://irbisa.com/ru/topic/ios-system-design/#q-73916)
