### 1. Чем отличаются unit-, интеграционные и UI-тесты, и зачем вообще писать тесты для iOS-приложения?

Unit-тест проверяет один тип в изоляции, с подменёнными зависимостями, и выполняется за миллисекунды; интеграционный тест запускает несколько настоящих частей вместе; UI-тест прогоняет собранное приложение через экраны так, как это делает пользователь.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66917)

### 2. Как выглядит хороший unit-тест, и что такое Arrange-Act-Assert?

Хороший unit-тест проверяет одно поведение, быстрый и детерминированный, и читается тремя блоками: Arrange (готовим входные данные и подмены), Act (вызываем один тестируемый метод), Assert (проверяем наблюдаемый результат).

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66918)

### 3. Что делает `@testable import`, и что он требует от сборки?

`@testable import MyApp` позволяет тестовому таргету пользоваться `internal`-объявлениями модуля так, будто они `public`, поэтому тестировать можно, не расширяя доступ в продакшен-коде. Работает это только если модуль собран с включённой поддержкой тестирования.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66919)

### 4. Что делают `setUp` и `tearDown` в XCTest, и сколько экземпляров класса тест-кейса создаёт XCTest?

XCTest создаёт отдельный экземпляр вашего подкласса `XCTestCase` для каждого тестового метода и вызывает `setUp` до и `tearDown` после каждого из них, поэтому свойства экземпляра всегда начинают с чистого листа.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66901)

### 5. Этот тест зелёный, хотя `FailingAPI` всегда возвращает ошибку. Почему ассерты никогда не падают?

```swift
final class ProfileViewModelTests: XCTestCase {
  func testLoadReportsOffline() {
    let sut = ProfileViewModel(api: FailingAPI(error: .offline))

    sut.load { result in
      XCTAssertEqual(result, .failure(.offline))
      XCTAssertEqual(sut.state, .error)
    }
  }
}

// ProfileViewModel: the completion fires after an await
func load(completion: @escaping (Result<Profile, APIError>) -> Void) {
  Task { completion(await api.fetch()) }
}
```

`load` вызывает completion позже, асинхронно, поэтому тестовый метод возвращается раньше, чем выполнится замыкание; в этот момент XCTest считает тест завершённым и успешным, и ассерты внутри замыкания для этого теста так и не проверяются.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66920)

### 6. Чем `#expect` отличается от `#require` в Swift Testing, и что они показывают такого, чего не может `XCTAssertTrue`?

`#expect` фиксирует падение и даёт тесту продолжиться; `try #require` бросает ошибку и останавливает тест: это то, что нужно для предусловия вроде разворачивания опционала. Оба реализованы как макросы, поэтому при падении показывают значение каждого подвыражения.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66902)

### 7. Как UI-тест на XCUITest взаимодействует с приложением, и чем он отличается от unit-теста?

UI-тест работает в собственном процессе-раннере и управляет установленным приложением снаружи через слой accessibility, как пользователь; он не может вызвать ваш код или прочитать его состояние, а может только найти элементы, взаимодействовать с ними и проверить, что на экране.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66921)

### 8. Чем Swift Testing отличается от XCTest, и что при миграции должно остаться в XCTest?

Swift Testing заменяет подклассы `XCTestCase` и семейство `XCTAssert` на функции `@Test`, макросы `#expect` и `#require` и трейты, а тесты по умолчанию запускает параллельно внутри одного процесса. У UI-тестов и performance-тестов на `measure` аналога нет, они остаются в XCTest.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66903)

### 9. Сколько кейсов запускает каждый из этих параметризованных тестов, и что пойдёт не так, если списки в `zip` разной длины?

```swift
enum Plan: CaseIterable { case free, pro, team }

@Test(arguments: Plan.allCases, [1, 5, 50])
func priceIsNeverNegative(plan: Plan, seats: Int) {
  #expect(Pricing.price(plan, seats: seats) >= 0)
}

@Test(arguments: zip(Plan.allCases, [0, 9, 29]))
func basePrice(plan: Plan, expected: Int) {
  #expect(Pricing.price(plan, seats: 1) == expected)
}
```

Первый запускает 9 кейсов, потому что две коллекции аргументов дают все комбинации (3 × 3); второй запускает 3, потому что `zip` составляет пары. Каждый кейс отображается отдельно, а более короткий список в `zip` молча отбрасывает лишние кейсы.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66922)

### 10. Что такое stub, spy, mock и fake, и как сделать их в Swift без библиотеки для моков?

Все четыре относятся к тестовым дублёрам (test doubles) настоящей зависимости: stub возвращает заготовленные ответы, spy ещё и записывает вызовы, mock проверяет заранее заданные ожидания, а fake представляет собой работающую облегчённую реализацию. В Swift их пишут руками или генерируют.

### 11. Найдите баг: этот тест падает, хотя `CheckoutViewModel.confirm()` действительно вызывает `track("purchase")`.

```swift
protocol Analytics { mutating func track(_ event: String) }
struct AnalyticsSpy: Analytics {
  private(set) var events: [String] = []
  mutating func track(_ event: String) { events.append(event) }
}
final class CheckoutViewModel {
  private var analytics: any Analytics
  init(analytics: any Analytics) { self.analytics = analytics }
  func confirm() { analytics.track("purchase") }
}
@Test func confirmTracksPurchase() {
  let spy = AnalyticsSpy()
  let sut = CheckoutViewModel(analytics: spy)
  sut.confirm()
  #expect(spy.events == ["purchase"])
}
```

`AnalyticsSpy` является структурой, поэтому при передаче в `CheckoutViewModel` она копируется: `confirm()` записывает `"purchase"` в копию внутри view model, а у `spy` в тесте массив `events` остаётся пустым. Тест падает, хотя продакшен-код верный.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66927)

### 12. Почему `wait(for:timeout:)` зависает в `async`-тесте XCTest, и когда при async/await всё ещё нужен expectation?

`wait(for:timeout:)` блокирует поток, на котором вызван, а в `async`-тесте этот поток принадлежит кооперативному пулу, который нужен ожидаемой работе, поэтому тест может попасть в deadlock; в `async`-тесте используйте `await fulfillment(of:timeout:)`: он приостанавливается, а не блокирует.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66904)

### 13. Тест вызывает `load()` у `@MainActor` view model и сразу проверяет состояние, а оно всё ещё `.idle`. Почему, и как исправить тест?

`load()` почти наверняка запускает `Task` и сразу возвращается, поэтому проверка выполняется раньше, чем тело задачи успело выполниться хотя бы раз. Сделайте работу ожидаемой и дождитесь её через `await`, а не через сон или yield.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66906)

### 14. Как доказать, что событие аналитики так и не отправилось, не платя в каждом прогоне пять секунд ожидания на inverted expectation?

Обычно ждать вообще не нужно: внедрите spy вместо приёмника аналитики, доведите код до точки, которую можно дождаться через `await`, и проверьте, что spy ничего не записал. Это точно и мгновенно.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66907)

### 15. Что проверяет teardown-блок в этом тесте, и почему он падает для этой view model?

```swift
final class FeedViewModel {
  private let service: FeedService
  private(set) var items: [Post] = []

  init(service: FeedService) {
    self.service = service
    service.onUpdate = { posts in self.items = posts }
  }
}

func testFeedViewModelIsReleased() {
  let sut = FeedViewModel(service: FeedService())
  addTeardownBlock { [weak sut] in
    XCTAssertNil(sut, "FeedViewModel leaked")
  }
}
```

Он проверяет утечку памяти: после возврата из тестового метода на `sut` не должно указывать ничего, кроме слабого захвата, значит, он обязан быть `nil`. Но это не так: view model владеет `service`, а `service.onUpdate` захватывает `self` сильно, и получается цикл сильных ссылок (retain cycle).

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66924)

### 16. Как тестировать SwiftUI-view, если в unit-тесте нельзя посмотреть, что отрисовал `body`?

Вынесите решения из view в модель и покройте её unit-тестами; пиксели проверяйте snapshot-тестами, а поведение через XCUITest. Apple не даёт API, который отдал бы unit-тесту отрисованное дерево SwiftUI.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66915)

### 17. Что такое snapshot-тесты, и почему они так часто падают на CI с едва заметным диффом?

Snapshot-тест отрисовывает view и сравнивает результат с эталонным изображением или текстовым дампом, закоммиченным в репозиторий. Так ловятся визуальные регрессии, которые не поймает ни один ассерт. На CI он падает потому, что отрисовка зависит от симулятора, ОС и машины, на которых сделан эталон.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66908)

### 18. Сьют XCUITest зелёный на английском и красный в день, когда пришла немецкая сборка. По чему матчились запросы, и по чему должны?

Они матчились по label, то есть переведённому тексту, который видит пользователь. Запросы должны матчиться по `accessibilityIdentifier`: он не локализуется и не озвучивается VoiceOver.

### 19. UI-тесту нужен залогиненный пользователь с тремя товарами в корзине. Как привести приложение в это состояние, не проходя вход нажатиями?

Передайте сценарий при запуске, и пусть приложение соберёт себя из стабов: UI-тест работает в другом процессе, поэтому `launchArguments` и `launchEnvironment` служат основным каналом в приложение.

### 20. Что на самом деле измеряет покрытие кода в Xcode, и почему view model с покрытием 87% всё равно уезжает с багом?

Оно измеряет, какие участки кода хотя бы раз выполнились во время тестов, и ничего не говорит о том, проверялось ли что-то ассертами и какие комбинации входных данных прогонялись. 87% означают, что 13% точно не протестированы, а не то, что остальное протестировано.

### 21. Что такое TDD, и где в iOS-разработке он окупается, а где нет?

Разработка через тестирование (TDD) означает сначала падающий тест, затем минимальный код, чтобы он прошёл, затем рефакторинг при зелёных тестах: red, green, refactor. Больше всего окупается на логике с понятными входами и выходами и меньше всего на вёрстке и экспериментальном UI.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66925)

### 22. Как настроить тестовые джобы iOS-пайплайна: что запускается на каждом pull request, а что на мерж или по ночам?

На каждом pull request запускайте быстрые детерминированные наборы (unit- и интеграционные тесты по тест-плану Smoke), а медленные (полный UI, snapshot-тесты, производительность) переносите на мерж или на ночь.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66926)

### 23. Включение параллельного тестирования сократило прогон с 20 минут до 6, и четыре теста начали падать случайно. Что изменила параллельность?

Тесты перестали владеть машиной в одиночку: XCTest распределяет тестовые классы по клонированным процессам и симуляторам, а Swift Testing ещё и выполняет тесты конкурентно внутри одного процесса. Тесты, полагавшиеся на общее состояние или фиксированный порядок, теперь падают в зависимости от тайминга.

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66912)

### 24. Один XCUITest падает примерно в одном из восьми прогонов на CI и ни разу на вашем ноутбуке. Как отличить настоящую гонку от недостающего ожидания?

Сначала добейтесь падения по требованию, затем меняйте одну вещь: если помогло более долгое ожидание, это была синхронизация; если тест падает и с таймаутом в 30 секунд, приложение пришло в неверное состояние, и это настоящая гонка (race condition).

[Полный ответ →](https://irbisa.com/ru/topic/ios-testing/#q-66914)

### 25. View controller на 900 строк вызывает `AnalyticsManager.shared`, `URLSession.shared`, `UserDefaults.standard` и `Date()`. Как покрыть его тестами уже на этой неделе?

Сделайте шов (seam) на каждом из этих четырёх вызовов и больше ничего не меняйте: целью должен стать объект, который можно создать в тесте без глобальных зависимостей, а не переписанный экран.
