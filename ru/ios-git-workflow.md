### 1. Каждой сборке, загруженной в App Store Connect, ставят тег вроде `v1.8.0-412`. Что такое коммит, ветка и тег и почему сборку помечают тегом, а не запоминают ветку?

Коммит хранит неизменяемый снимок проекта со ссылкой на родителя, ветка служит именем, которое сдвигается вперёд с каждым новым коммитом, а **тег** намертво привязан к одному коммиту, поэтому `v1.8.0-412` всегда показывает, какой именно код Apple проверяла как сборку 412.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75901)

### 2. В меню Integrate у Xcode есть Fetch Changes и Pull. Что делает каждая команда и зачем включать `pull.rebase` для локального `main`?

**Fetch Changes** выполняет `git fetch`: скачивает новые коммиты и обновляет `origin/main`, не трогая вашу ветку и файлы, а Pull ещё и мержит или ребейзит их в текущую ветку. С настройкой `pull.rebase` ваши локальные коммиты встают сверху, а не порождают merge-коммит.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75902)

### 3. Мержить `main` в свою ветку `feature/paywall` или ребейзить её на `main`, если обе стороны постоянно правят `project.pbxproj`?

Merge приносит `main` одним merge-коммитом, а **rebase** переигрывает каждый ваш коммит поверх `main` с новыми хешами. Когда `project.pbxproj` меняется с обеих сторон, merge разрешает этот файл один раз, а rebase, возможно, на каждом коммите.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75903)

### 4. Как разрешить merge-конфликт в Swift-файле и почему конфликты в storyboard разрешать намного сложнее?

В **Swift-файле** вы читаете обе стороны между маркерами, пишете код, сохраняющий оба намерения, удаляете маркеры и гоняете сборку с тестами. Storyboard же представляет собой сгенерированный XML со случайными id объектов и фреймами, и его конфликты человеку почти не понять.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75904)

### 5. Нужно починить баг в `release/2.1`, а в вашей ветке незакоммиченные правки SwiftUI. Когда хватит `git stash`, а когда лучше второй worktree?

**`git stash`** откладывает незакоммиченные правки, чтобы можно было сменить ветку, а `git stash pop` потом их возвращает; для фикса на несколько часов `git worktree add` извлекает `release/2.1` в отдельную папку, и ваша ветка вместе с состоянием Xcode остаётся нетронутой.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75905)

### 6. Какие файлы Xcode относятся в `.gitignore`, а какие обязательно коммитить, и почему коллега не видит схему, которую вы создали?

Игнорируйте пользовательские и сгенерированные файлы вроде `xcuserdata/`, `DerivedData/` и `*.xcuserstate`, а проект, `Package.resolved` и **общие схемы** коммитьте: схема без галочки Shared лежит в `xcuserdata`, а с галочкой её файл переезжает в `xcshareddata/xcschemes`.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75906)

### 7. Ваша ветка и `main` конфликтуют и в `project.pbxproj`, и в `Package.resolved`. Как разрешить каждый файл и как сделать, чтобы конфликты в `.pbxproj` не возвращались?

В **`project.pbxproj`** оставьте записи обеих сторон во всех секциях, потому что каждый добавленный файл упоминается в нескольких местах, затем проверьте файл и соберите проект. `Package.resolved` создаёт резолвер: возьмите копию из `main` и дайте Xcode заново разрешить ваши добавления.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75907)

### 8. Каждый раз начиная с состояния ниже: что меняет каждая команда и какие из них могут потерять работу?

```shell
# feature/settings, nothing pushed yet
#   b4 Add notification toggle   <- HEAD
# staged:   Info.plist (CFBundleVersion 411 -> 412)
# unstaged: Sources/Settings/SettingsView.swift

git restore Sources/Settings/SettingsView.swift   # A
git restore --staged Info.plist                   # B
git reset --soft HEAD~1                           # C
git reset --hard                                  # D
```

A выбрасывает непроиндексированные правки в `SettingsView.swift`, B лишь убирает `Info.plist` из индекса, C отменяет коммит `b4`, оставляя его изменения в индексе, а **`git reset --hard`** (D) стирает все правки, и в индексе, и в рабочей копии. Безвозвратно потерять работу могут A и D.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75908)

### 9. Один коммит смешивает новый экран на SwiftUI и перестановку 400 строк в `project.pbxproj`. Как разделить его интерактивным rebase и безопасно запушить результат?

Пометьте коммит как `edit` в `git rebase -i`; когда Git на нём остановится, `git reset HEAD~` отменит коммит, но оставит изменения, и вы закоммитите проектный файл и экран по отдельности, выполните `git rebase --continue` и запушите с **`--force-with-lease`**.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75909)

### 10. После интерактивного rebase из `feature/widgets` пропал коммит с timeline для WidgetKit. Как найти его через `git reflog` и вернуть?

Rebase пишет новые коммиты и переносит ветку, но старые коммиты остаются в репозитории: **`git reflog`** по-прежнему показывает их с хешами, поэтому `git cherry-pick <sha>` вернёт потерянный коммит, а `git reset --hard ORIG_HEAD` отменит весь rebase.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75910)

### 11. Приложение теперь падает при запуске только на iOS 17, а с последней хорошей сборки в TestFlight прибавилось 120 коммитов. Как найти виновника через `git bisect run`?

Отметьте `HEAD` как плохой, а тег последней хорошей сборки как хороший, и пусть **`git bisect run`** запускает скрипт, который собирает приложение и гоняет один UI-тест запуска на симуляторе iOS 17; на 120 коммитов хватит примерно семи шагов.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75911)

### 12. Как сообщения коммитов и Conventional Commits вписываются в iOS-релиз, где `MARKETING_VERSION` и номер сборки меняются при каждой загрузке в App Store?

У коммита короткая тема в повелительном наклонении и тело, объясняющее зачем; с **Conventional Commits** инструмент релиза по `feat`, `fix` и `!` предлагает следующий `MARKETING_VERSION`, а номер сборки `CURRENT_PROJECT_VERSION`, который App Store Connect требует увеличивать, поднимает только CI.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75912)

### 13. Что делает pull request в iOS-проекте удобным для ревью и что вы проверяете в первую очередь, когда ревьюите чужой?

Хороший iOS pull request маленький, объясняет, зачем он нужен и как проверен, и показывает **скриншоты** каждого изменённого экрана в светлой и тёмной теме и при крупном Dynamic Type; ревьюер смотрит сначала на поведение, потоки и память, а потом на стиль.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75913)

### 14. App Review может занять сутки и больше. Как с этим справляются GitFlow, GitHub flow и trunk-based development и что вы выберете для iOS-приложения?

Большинство iOS-команд работает по **trunk-based development** с короткими релизными ветками: маленькие pull request вливаются в `main`, для отправки отрезается `release/1.9`, а фиксы, найденные во время ревью, сначала попадают в `main` и переносятся в релизную ветку через cherry-pick.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75914)

### 15. Какие проверки стоит класть в pre-commit хук iOS-проекта и почему CI всё равно должен их повторять?

**Pre-commit хук** должен запускать только быстрые проверки на проиндексированных Swift-файлах, например SwiftFormat и SwiftLint, а сборка и тесты остаются в CI: хуки лежат в `.git/hooks`, не клонируются вместе с репозиторием, а `git commit --no-verify` их пропускает.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75915)

### 16. Ключ App Store Connect API `AuthKey_7XK2P9.p8` запушили вместе с настройкой fastlane. Что делать и почему удаления в следующем коммите недостаточно?

**Отзовите ключ** в App Store Connect в разделе Users and Access, Integrations и создайте новый, который хранится как секрет CI: в истории каждого клона старый файл остаётся, а удаляющий коммит лишь прячет его из последней версии.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75916)

### 17. PR #88 с онбордингом откатили в `main`, потому что он падал при первом запуске. Исправленная ветка потом смержилась без конфликтов, но новый онбординг так и не появился. Что пошло не так?

```shell
git switch main
git merge --no-ff feature/onboarding-v2     # PR #88: six commits, new SwiftUI flow
git revert -m 1 HEAD                        # crash on first launch: back it out
git push

git switch feature/onboarding-v2
git commit -am "fix: no force unwrap of the stored user on first launch"
git switch main
git merge feature/onboarding-v2             # 1 file changed
```

**Revert-коммит** отменил код онбординга, но шесть коммитов фичи по-прежнему входят в историю `main`, поэтому второй merge добавляет только новое в ветке: исправление в одном файле, наложенное на `main`, где фичи уже нет.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75917)

### 18. Приложение, его виджет-расширение и второе приложение делят код сети и UI. Локальные Swift-пакеты в одном репозитории или отдельные репозитории с тегами версий?

Начните с **локальных Swift-пакетов** в репозитории приложения: приложения и расширения меняют общий код и его вызовы в одном pull request, а Xcode собирает всё из исходников. Выносите пакет в отдельный репозиторий, только когда у него появляются свои владельцы или внешние потребители.

[Полный ответ →](https://irbisa.com/ru/topic/ios-git-workflow/#q-75918)
